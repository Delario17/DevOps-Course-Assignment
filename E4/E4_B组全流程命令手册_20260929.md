# E4 B 组（DRAFT）全流程命令手册

适用：已分到阿里云 ECS 公网 IP、使用 B 组模板的学生。你只需要老师私发的 **本组 IP、登录账号和当前密码**，不用另注册阿里云账号。密码只在 SSH 提示时输入，不写进命令、截图或仓库。文中的 `<...>` 必须换成自己的信息。

## 1. 在自己电脑上连接服务器

Windows 请打开不带 “x86” 的 PowerShell；Mac 打开“终端”。先检查：

```text
ssh -V
```

出现 `OpenSSH_...` 就可以继续。Windows 若提示找不到 `ssh`，在“设置 → 应用 → 可选功能”安装 **OpenSSH 客户端**，重新打开 PowerShell；也可用 Git Bash 的 `ssh`。然后连接：

```text
ssh -l <老师给的账号> <本组公网IP>
```

第一次连接要先核对主机指纹，再完整输入 `yes`。密码输入时不显示字符。看到 `root@...#` 或 `用户名@...$` 才表示进入服务器；从此处开始，下文的 `sh` 命令都在**服务器**运行。

## 2. 全组只做一次：准备本组仓库

组长先确认服务器上的 Docker 已就绪：

```sh
cat /etc/os-release | grep PRETTY_NAME
uname -m
docker --version
docker version
docker compose version
docker buildx version
```

若 Docker 已能正常使用，直接继续，**每名学生不用重装**。若未安装，由教师、助教或拥有管理员权限的组长在确认 Ubuntu 版本后，按 `setup/bootstrap_ubuntu.sh` 全组初始化一次；这不是必须由老师本人执行。`docker --version` 只显示客户端版本，仍要通过后续实际构建验证镜像能否下载。

**组长**额外克隆一次本组远程仓库，用于确认 B 模板已经就绪。仓库若已有模板，跳过下面的初始化提交；不要覆盖现有文件。每位组员（包括组长）之后仍按第 3 节在自己的学号目录另行克隆并运行。以下 `<本组仓库地址>` 和 `<组长学号>` 是占位符，不能原样输入：

```sh
mkdir -p /root/e4-group-setup
cd /root/e4-group-setup
git clone <本组仓库地址> draft
cd draft
git remote -v
ls -la
```

**仅当远程仓库还没有 B 模板时**，组长才执行一次以下初始化；这不是各组员的 E4 个人提交：

```sh
tar -C /root/E4实验包/B-draft --exclude='./.git' --exclude='./work' --exclude='./.env' -cf - . | tar -xf -
git config --local user.name '<组长学号>'
git config --local user.email '<组长在 Git 平台验证过的邮箱或隐私邮箱>'
git status --short
git add .
git diff --cached --check
git commit -m 'E4: add B group environment'
git push -u origin HEAD
```

初始化前确认没有 `.env`、真实密钥、`work/` 或 Python 缓存。若本组仓库已有代码，组长先查看目录，避免覆盖现有成果。全体组员从本组仓库克隆，**不要**直接在 `/root/E4实验包/B-draft` 模板目录做个人实验。E4 不要求组员个人提交或由组长合并。

## 3. 每名学生：克隆、设置身份、自检

在服务器上用自己的学号建目录，以下示例把仓库放在 `draft/`：

```sh
mkdir -p /root/<学号>
cd /root/<学号>
git clone <本组仓库地址> draft
cd draft
git config --local user.name '<学号>'
git config --local user.email '<学号>@localhost'
git rev-parse HEAD
git status --short
make doctor
```

只用 `--local`，因为同组共用一个服务器登录账号。E4 普通组员只克隆、不推送，`学号@localhost` 是本地示例值，不需要 Git 平台账号。`make doctor` 显示“环境自检：通过”、`problems: []` 才能继续；CPU、内存、磁盘低于**建议值**时会出现 `warnings`。E4 B 组样例的最低可见内存为 3.5 GiB；以后构建真实项目仍要按负载核对资源。

## 4. 确认 B 组镜像来源

B 组有两种基础镜像：Python 和 Docker 客户端。模板从可访问的镜像站读取，digest 仍固定内容。服务器为 `x86_64` 时，查看镜像索引是否包含 `linux/amd64`：

```sh
grep '^ARG .*IMAGE=' services/draft/Dockerfile
grep '^FROM ' fixtures/draft/Dockerfile.broken
docker buildx imagetools inspect 'm.daocloud.io/docker.io/library/python@sha256:f82c96458eedc847b233e582eb31336f4954b39cae020b6dcf5b3ed0e5cbcd74'
docker buildx imagetools inspect 'm.daocloud.io/docker.io/library/docker@sha256:9190b0613792e658a7783cf14b2d5ace5941bb68ede7276922ea36ee457d76ad'
```

试用 ECS 直连 Docker Hub 曾超时，以上固定 digest 的镜像站地址已在试用 ECS 核验。构建还会访问 Debian `apt` 与 Python 包源；镜像站可访问不保证后两者同样快。镜像地址变动应由组长统一修订、提交，其他组员拉取同一提交。

## 5. 完整运行 E4

在**自己的克隆根目录**执行：

```sh
git pull --ff-only
git status --short
make all
```

`make all` 按顺序运行 `doctor → build → test → smoke → scan`。第一次构建会自动生成权限为 600 的 `.env`；E4 骨架测试不需要真实 LLM API Key，保持示例内容即可。构建可能因首次下载镜像、Debian 软件包而较慢；不要同时再开第二次构建。

成功运行应看到：

| 步骤 | 证据文件（同一 `work/<时间>/`） | B 组检查点 |
| --- | --- | --- |
| 环境自检 | `env.json` | `problems` 为空；Git 身份是自己学号 |
| 构建 | `build.log`、`image.json`、`toolchain.lock` | 镜像成功；记录 digest、镜像 ID、Docker CLI 等版本 |
| 单测 | `test.log` | 当前模板 `4 passed` |
| 冒烟 | `smoke.json` | `docker_server` 有版本；`build_exit_code` 非 0；`make_error_line` 含 `make: not found`；`passed: true` |
| 密钥检查 | `secret-scan.txt` | “密钥检查：未发现问题” |

**冒烟样例故意构建失败。** `Dockerfile.broken` 中执行 `make`，但基础镜像没有安装 `make`。`build_exit_code: 1` 与 `passed: true` 可以同时出现：前者是样例构建失败，后者表示 DRAFT 服务成功识别并记录了预期失败。`log_tail` 只有末尾 8 行，不保证包含报错；看 `make_error_line`。本次 ECS 联测中容器里的 Docker **客户端**为 28.5.1，`docker_server` 显示宿主机引擎 29.1.3。容器通过 `docker.sock` 使用宿主机引擎，无需再装一套引擎。

## 6. 检查证据和密钥扫描

`make all` 结束会打印证据目录。若忘记目录名：

```sh
RUN_DIR=$(ls -td work/* | head -n 1)
printf '证据目录：%s\n' "$RUN_DIR"
ls -lh "$RUN_DIR"
cat "$RUN_DIR/test.log"
cat "$RUN_DIR/smoke.json"
cat "$RUN_DIR/secret-scan.txt"
git rev-parse HEAD
git ls-files .env
git status --short
```

若此前失败后重试过，最新目录须对应**成功**的那次运行。`git ls-files .env` 应没有输出。用假 Key 检查扫描器（只在自己的克隆里做，**不要提交**）：

```sh
printf 'api_key = "sk-demo1234567890abcdefghijk"\n' > leak-demo.txt
git add leak-demo.txt
make scan
git rm --cached -q leak-demo.txt
rm leak-demo.txt
make scan
git status --short
```

第一次 `make scan` 应报出假 Key 并返回错误；删除假文件后第二次应通过。两次扫描各生成一个新的 `work/<时间>/`，不要与完整 `make all` 的证据目录混淆。

## 7. 第二名组员重跑

另一名组员在自己的学号目录重新克隆、配置自己的本地 Git 身份，再运行 `make all`。两人记录各自完整的 `git rev-parse HEAD`，比较 `toolchain.lock`、`test.log` 与 `smoke.json` 的**结论**。镜像 ID、运行时间、日志行数可能不同；工具版本和预期结果应一致。试用 ECS 上的两个模拟学生克隆均使用模板提交 `06a883180c6c0ffee940c667fb0e0047ac67fa8a`，成功运行的证据目录分别为 `work/20260929-030934/`、`work/20260929-031236/`。两份克隆共用同一台服务器及 Docker 缓存；这只是课堂流程预演，正式组员仍各自留证据。

### 7.1 E4 的记录范围

每名组员只需记下自己的学号目录、`git rev-parse HEAD` 的源码 SHA、成功的 `work/<时间>/` 和与另一名组员的对照结论。`git remote -v` 应显示本组远程仓库地址。`work/` 默认被忽略，因此 E4 的个人运行不会出现在小组仓库的提交历史中；本节不要求个人创建分支、提交、推送，也不要求组长审查合并。本次教师试跑从服务器本地模板克隆，只验证了实验环境和命令，没有测试课程平台远程推送。

## 8. E5 如何接续

E4 的 `smoke.json` 保留退出码、关键错误行与构建日志末尾，**不是 E5 要求的完整原始日志**。E5 在同一服务环境中按 E5 步骤重新运行 `docker build --progress=plain`，把完整标准输出、标准错误与退出码写进仓库的 `work/`，再开展定位与修复。`make shell` 会把宿主机 `work/` 挂到容器的 `/app/work`；但在本次以 root 登录的 ECS 上，`make shell` 会按宿主机 UID 进入容器，不能用它证明默认 `app` 用户有 Docker 权限。E4 的 `make smoke` 以默认 `app` 用户执行，已验证这点。

`docker.sock` 的访问权限相当于控制宿主机 Docker。只构建课程指定的项目，不开放 Docker API 2375/2376 端口，也不要清理其他组员的镜像与缓存。

## 9. 常见问题

| 现象 | 处理 |
| --- | --- |
| `ssh` 找不到 | Windows 安装 OpenSSH 客户端并重新打开 PowerShell；Mac 先用 `ssh -V` 检查 |
| `make doctor` 失败 | 查看 `env.json` 的 `problems`，核对 Git 本地身份和 Docker 工具 |
| Docker Hub 超时 | 核对本组最新模板的镜像站路径和固定 digest；看第 4 节 |
| Debian `apt` 下载很慢 | 看 `build.log` 中 `Get:` 是否仍变化；不要并行构建 |
| `docker.sock permission denied` | 用 `make` 运行，让 Makefile 注入 `DOCKER_GID`；保留完整报错给助教 |
| `3/4 passed` 后命令不返回 | 核对新版 Makefile 的 Compose `run` 带 `-T --interactive=false` |
| 冒烟中 `build_exit_code` 非零 | 先看 `passed`；缺少 `make` 的预期失败应被识别为通过 |
| `make_error_line` 为空或 `passed: false` | 保存 `smoke.json`，核对镜像、docker.sock 权限与构建日志 |

本次 E4 结束时，每人应能指出自己的成功证据目录和所测源码 SHA，说明 `make all` 结论及与另一名组员的对照。这里的 SHA 是运行时小组模板的版本号，不是要求个人新建一个提交。
